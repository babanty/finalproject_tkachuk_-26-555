# Архитектура

Исходное задание: `../Задание.txt` в родительском каталоге проекта. Подробный план также находится на уровень выше и не входит в Git.

Пакет `valutatrade_hub` расположен в корне проекта согласно схеме нового задания. Старые учебные требования предполагали `src/`, но новое задание задаёт структуру пакета в корне; сборка настроена явно. Имя дистрибутива `finalproject-tkachuk-m26-555` отличается от импортируемого имени `valutatrade_hub` и каталога с кириллицей.

Весь ввод команд будет обрабатываться в `cli/interface.py`. Доменные модели реализованы в `core/`, где далее появятся сценарии торговли. JSON-хранилище и настройки появятся в `infra/`, API-клиенты и обновление курсов — в `parser_service/`. Импорт модулей не должен создавать файлы, обращаться к сети или запускать REPL.

Сохраняемые данные будут лежать в `data/` относительно рабочего каталога либо по явно указанному пути; локальные данные не попадут в Git. Канонический формат курсов — `rates.json` с `pairs` и `last_refresh`. Пары нормализуются к USD, TTL применяется к каждой паре отдельно. Купля списывает USD, продажа начисляет USD; для начального виртуального капитала будет явная команда `deposit`.

Эти решения согласованы с `IMPLEMENTATION_PLAN.md` в родительском каталоге. Более подробные контракты добавятся вместе с реализацией.

## Контракты моделей — этап 2

- `User(...)` восстанавливает пользователя из сохранённых хеша, соли и aware datetime. `User.create(...)` принимает открытый пароль, генерирует индивидуальную соль и вычисляет SHA-256 от UTF-8 строки `password + salt`. `change_password()` меняет также соль, `verify_password()` использует `hmac.compare_digest`. Имя обрезается по краям и сохраняет регистр; пароль не обрезается и должен содержать минимум четыре символа. Все поля имеют свойства, идентификатор и дата доступны только для чтения. `get_user_info()` возвращает отдельный словарь без хеша и соли. Дата нормализуется в UTC.
- `Wallet(currency_code, balance=0.0)` работает с известными валютами. Код доступен только для чтения. `balance`, `deposit()` и `withdraw()` валидируют значения до присваивания: int/float разрешены, bool, строки, NaN, inf и переполнение отклоняются. Снятие ровно всего баланса разрешено, любой перерасход вызывает `InsufficientFundsError`. Хранимый баланс не округляется; финансовые числа по учебному ТЗ представлены float.
- `Portfolio(user_id, wallets=None, *, user, rate_provider)` связывает владельца и кошельки. Свойство `wallets` возвращает поверхностную копию словаря, а сами `Wallet` остаются объектами портфеля. Повторное `add_currency()` возвращает тот же кошелёк; `get_wallet()` возвращает None, если известная валюта отсутствует. Неверный владелец, конфликт ключа и валюты кошелька, дубли после нормализации отклоняются.
- `rate_provider(from_code, to_code) -> float` внедряется в портфель. `get_total_value()` вызывает его только для ненулевых балансов, отличающихся от базы; неизвестная база отклоняется даже для пустого портфеля. Невалидный курс, ошибка поставщика и переполнение не превращаются в частичный итог. На этапе 5 адаптер будет передавать числовой `rate` из `RateQuote`.
- Валюты — неизменяемые dataclass-объекты с публичными метаданными и общим абстрактным интерфейсом `get_display_info()`. Реестр выдаёт готовые объекты USD/EUR/GBP/RUB/BTC/ETH/SOL. Не загруженная капитализация криптовалют обозначается `N/A`; реестр не содержит вымышленных актуальных цен.
- Общая иерархия ошибок — `ValutaTradeError`, `ValidationError`, `InsufficientFundsError`, `CurrencyNotFoundError`, `ApiRequestError`. Неверный формат кода вызывает ValidationError, правильный, но неподдерживаемый код — CurrencyNotFoundError. Валидация вынесена в `core/utils.py`.

## Конфигурация и JSON — этап 3

`SettingsLoader` и `DatabaseManager` реализованы через `__new__`: этот способ даёт один экземпляр без собственного метакласса. Конструирование и первая настройка защищены `RLock`; повторный `__init__` сохраняет состояние, а новая явно противоречащая конфигурация отклоняется. Singleton создаётся при обращении приложения, а не при импорте. Тестовые фикстуры сбрасывают экземпляры между тестами; рабочий API такого сброса не предоставляет.

`default_config.json` является ресурсом пакета, поэтому наличие `pyproject.toml` в текущей папке не требуется. JSON-конфиг дополняет defaults, затем применяются переменные `VALUTATRADE_*`, затем явные overrides. Значения преобразуются в int/float/Path, проверяется конечность чисел и допустимость вариантов. Ключи `users_file`, `portfolios_file`, `rates_file`, `history_file` вычисляются из абсолютного data_dir. API-ключи загрузчик настроек не читает: они относятся к будущему ParserConfig.

`infra/json_io.py` содержит общий строгий reader и атомарный writer для Core и Parser Service. Reader отвергает дубли ключей, NaN/Infinity, повреждённый JSON и неверную UTF-8. Writer сначала сериализует с `allow_nan=False`, создаёт уникальный временный файл в том же каталоге, выполняет flush/fsync, закрывает handle и вызывает `os.replace`. При ошибке сохраняется прежний файл, cleanup касается только собственного временного файла.

`infra/serialization.py` восстанавливает модели, сохраняет hash/salt и ISO-дату с UTC `Z`, проверяет уникальность пользователей, соответствие владельцев и кошельков, схемы снимка и истории курсов. У пользователя должен быть ровно один портфель. Поля баланса не заменяются значением по умолчанию, если данные повреждены. Дополнительный список transactions сохраняется при обновлении кошельков; его полная предметная схема будет добавлена на этапе 6.

Все операции репозитория используют один отдельный `data/.store.lock` с конечным таймаутом через filelock. Файл блокировки сохраняется после освобождения; JSON заменяется независимо от него. Блокировка повторно захватывается тем же объектом: на этапе регистрации можно охватить одним `with database.locked()` выбор нового ID, чтение пользователей и `save_account()`.

`save_account()` сохраняет согласованную пару User/Portfolio. Если вторая запись не удалась, восстанавливает первый документ. Ошибка отката явно требует восстановления. Это компенсация обычной ошибки, а не ACID-гарантия при аварийном завершении процесса или питании. `update_portfolio()` читает новые экземпляры моделей под блокировкой и сохраняет обновлённый файл только после успешного callback; исключение callback не затрагивает диск. `initialize()` сначала проверяет все имеющиеся документы и лишь затем создаёт отсутствующие пустые файлы. Эти операции не выполняют запросов курса: usecases должны получить нужные котировки до начала изменения портфеля.
